# EVAA Stale-Price Liquidation Monitor (только чтение)

Инструмент для сбора доказательств находки про ликвидацию по устаревшей цене в EVAA.
Следит за **MAIN** пулом EVAA и шлёт алерты (Telegram) **только когда позиция
подтверждена — на реальном задеплоенном байткоде — как ликвидируемая прямо сейчас
через устаревшую, но всё ещё в пределах TTL, цену Pyth**, хотя по текущей цене она
здорова.

**Read-only.** Только `GET`-запросы и TVM get-методы в локальном sandbox-форке.
**Не отправляет транзакций**, не может двигать средства и не может никому навредить.

---

## Зачем это нужно

EVAA принимает цены Pyth возрастом до `prices_ttl = 180s`, `publish_gap` контролируется
атакующим и не ограничен сверху, а `is_liquidable` не делает независимой проверки
свежести. Поэтому ликвидатор может отправить подписанный *исторический* VAA от
кратковременного провала цены и ликвидировать позицию, которая **здорова по текущей
цене** — забрав себе ликвидационный бонус.

Эксплуатируемый случай требует позицию, у которой запас здоровья обнуляется в окне
180с. Этот монитор находит такие моменты в реальном времени.

> Примечание по scope: контракт **в скоупе** (репо `evaafi/contracts`, code-hash
> `08b54a3f…`, пул `EQCsOdQ…`) почти пустой. Реальный funded пул **MAIN** (`EQC8rU…`,
> code-hash `b90881c4…`) использует тот же оракул Pyth + `prices_ttl=180`, но другая
> версия кода. Этот монитор следит за MAIN для оценки реального impact.

## Как это работает — два уровня (точно, не эвристика)

### Уровень 1 — медленный полный пересчёт (`SCAN_INTERVAL_MS`, по умолчанию 5 мин)

Для каждого известного/собранного заёмщика:

1. Читает `oracles_info.feeds_data` (карта pyth→evaa) + децималы по каждому ассету из
   on-chain storage мастера MAIN, и текущие живые цены Pyth (Hermes `/latest`).
2. Форкает мастер + контракт пользователя в `@ton/sandbox`, читает реальные балансы
   через `getAccountBalances`.
3. Бинарным поиском находит **flip factor** `f*` — множитель цены коллатерала, при
   котором реальный `getIsLiquidable` переключается в `true`:
   - `f* >= 1` → уже ликвидируема **по текущей цене** (честная ликвидация, не этот баг).
   - `f* < 1` → сейчас здорова; станет ликвидируемой, если цена коллатерала упадёт до
     `f* × ref_price`.
4. Кэширует `{addr, collIds, flipFactor, refPrices, collUsd, debtUsd}` для каждой позиции
   (`data/flip_cache.json`) и сохраняет набор заёмщиков (`data/known_users.json`), чтобы
   неактивные позиции не терялись между пересчётами.

### Уровень 2 — быстрый watch живых цен (`FAST_INTERVAL_MS`, по умолчанию 25с)

1. Один дешёвый вызов Hermes за текущими ценами всех фидов.
2. Для каждой закэшированной позиции (с `f* < 1`) считает `ratio = live_price / ref_price`
   для её коллатерала. Если `ratio <= f* × (1 + TRIGGER_MARGIN)` — цена подошла близко
   (или прошла) закэшированную точку флипа — позиция **триггерится**.
3. Только для триггернутых позиций: берёт окно свежей-и-устаревшей-на-180с цены, снова
   форкает мастер + пользователя и вызывает реальный `getIsLiquidable` с обоими
   наборами цен (`userInfo`).
4. **Алерт только если подтверждено на реальном байткоде**:
   - `liqFresh=false, liqStale=true` → 🚨 баг с устаревшей ценой эксплуатируем *прямо
     сейчас*.
   - `liqFresh=true` → ⚠️ честная возможность ликвидации (информационно, не этот баг).

Никаких хардкоженых цен, никаких фиксированных порогов — каждый вердикт идёт из
задеплоенного байткода, и для закэшированного flip factor, и для финального
подтверждения.

## Как читать алерт

```
🚨 EVAA — CONFIRMED: liquidatable NOW via stale price
MAIN pool | TTL 180s
0:954AB6…51F26C TON→USDT
coll~$704 debt~$500 (≈$204 at stake)
Healthy at current price, but a real Pyth price from within the last 180s
makes getIsLiquidable=true. Verified on real contract bytecode (fork) just now.
```

Это значит: **прямо сейчас** ликвидатор, отправив реальный подписанный Pyth VAA
из последних 180с, может вызвать `liquidate` на этой позиции и это пройдёт успешно,
хотя позиция здорова по живой цене. Это живой, действующий экземпляр бага — не
"около порога" эвристика.

Вторичный алерт `⚠️ liquidatable at CURRENT price (honest)` — просто информационный,
обычная возможность ликвидации, не связанная с багом устаревшей цены.

## Установка

```bash
npm install
cp .env.example .env     # затем заполнить три секрета
```

`.env`:

```
TONCENTER_KEY=<toncenter v3 api key>     # https://toncenter.com
TELEGRAM_TOKEN=<bot token>               # @BotFather
TELEGRAM_CHAT=<your chat id>             # numeric id
```

Секреты загружаются маленьким встроенным ридером `.env` (без зависимостей). `.env`
в git-ignore — никогда не коммитить.

## Использование

```bash
node index.js --tg-test    # отправить тестовое сообщение в Telegram
node index.js --once       # прогнать tier1 (полный пересчёт) раз, потом tier2 раз, выйти
node index.js              # работать вечно: tier1 каждые SCAN_INTERVAL_MS,
                            #                  tier2 каждые FAST_INTERVAL_MS
```

Вывод: лог в консоль с закэшированными позициями и триггернутыми/подтверждёнными
проверками, Telegram-алерт при подтверждении, persisted state в
`data/known_users.json` и `data/flip_cache.json`.

---

## Конфиг (`config.js`)

| ключ | значение | по умолчанию |
|---|---|---|
| `MAIN_POOL` | пул для мониторинга | EVAA MAIN |
| `SCAN_INTERVAL_MS` | период tier1 (полный пересчёт) | 5 мин |
| `FAST_INTERVAL_MS` | период tier2 (watch живых цен) | 25 с |
| `TRIGGER_MARGIN` | tier2 триггерит on-chain подтверждение если `live/ref <= f*×(1+margin)` | 0.03 |
| `CANDIDATE_PAGES` | страниц toncenter с недавними tx для сбора кандидатов | 8 |
| `MAX_USERS_PER_SCAN` | лимит пользователей на tier1 | 400 |
| `STALE_WINDOW_S` | EVAA `prices_ttl` (окно бага) | 180 |

## Ограничения / честность

- Условие триггера tier2 (`ratio <= f*×(1+margin)`) — дешёвый пре-фильтр только по
  живой цене — может как пропустить быстрое внутритиковое движение между опросами,
  так и сработать лишний раз; сам **алерт** никогда не эвристика, он всегда идёт из
  свежего on-chain подтверждения `getIsLiquidable`.
- Позиции с `f* >= 1` (уже ликвидируемые по живой цене) исключены из триггеров tier2 —
  tier1 логирует их как "already-liquidatable@fresh" (честная территория, не этот баг).
- Read-only.
