## 1. Методика и ограничения

Цель этапа: отделить bounty-ready сценарии от гипотез, которые выглядят опасно на уровне модели, но не подтверждаются исходниками.

Что было сделано:

- повторно проверены скачанные mainnet/testnet Leo-программы;
- сверены сценарии из `№3.md` и приоритеты из `№4.md` с реальными finalize/async путями;
- прогнаны локальные state-machine модели в `stage4_verification/verification_models.mjs`;
- для каждого сценария выставлен статус: `REFUTED_BY_SOURCE`, `SOURCE_CONFIRMED_BEHAVIOR`, `SOURCE_CONFIRMED_EDGE_CASE`, `NEEDS_PATH_PROOF`.

Live-исполнение на mainnet/testnet не выполнялось: в рабочей папке нет безопасного кошелька, faucet-финансирования, выделенного RPC-профиля и разрешенного набора тестовых активов. Поэтому результаты ниже являются pre-submit verification: они готовы для подготовки controlled testnet PoC, но не должны подаваться как “эксплуатировано on-chain” без отдельного прогона.

Команды воспроизведения локальной проверки:

```powershell
node .\stage3_pocs\scenario_models.mjs
node .\stage4_verification\verification_models.mjs
```

## 3. Топ-10 сценариев после верификации

### 1. USDCX: mint через previous freeze root внутри grace window

**Статус:** `SOURCE_CONFIRMED_BEHAVIOR`  
**Контракты:** `usdcx_bridge.aleo`, `usdcx_freezelist.aleo`, `usdcx_stablecoin.aleo`  
**Источник:** `aleo_context/raw/mainnet/program_sources/usdcx_bridge.aleo.aleo:561`

Суть: `finalize mint_private` принимает текущий freeze root, но если переданный root не равен текущему, код допускает previous root `freeze_list_root[2u8]`, пока `root_updated_height + block_height_window > block.height`.

PoC-ready шаги:

1. Зафиксировать `freeze_list_root[1u8]`, `freeze_list_root[2u8]`, `root_updated_height`, `block_height_window`.
2. Выбрать адрес, который разрешен старым root, но должен быть запрещен новым root после freeze update.
3. Подготовить Circle attestation, nullifier и mint future.
4. Отправить `mint_private` до истечения окна `root_updated_height + block_height_window`.
5. Проверить, принимает ли bridge старый root и происходит ли mint.

Expected: mint для frozen/ново-заблокированного адреса должен быть невозможен сразу после обновления freeze list.  
Actual by source: previous root принимается внутри окна.  
Impact: потенциально высокий, если окно позволяет обойти freeze policy для bridge mint.  
Reproducibility: высокая при наличии тестового freeze update и attestation.  
NonObviousness: высокая, потому что баг живет в сочетании bridge attestation + freeze root history + block window.  
Открытый вопрос: является ли grace window намеренной политикой Circle/USDCX, или она нарушает ожидаемую семантику freeze.

### 2. `credits.aleo`: partial unbond превращается в full unbond около минимального остатка

**Статус:** `SOURCE_CONFIRMED_BEHAVIOR`  
**Контракты:** `credits.aleo`, staking wrappers (`whalepool_easystaking_v3.aleo` и аналоги)  
**Источник:** `aleo_context/raw/mainnet/program_sources/credits.aleo.aleo:153`

Суть: в `finalize unbond_public` вычисляется остаток `bonded - requested`; если он меньше `10_000_000_000u64`, unbond amount становится не `requested`, а весь bonded balance.

PoC-ready шаги:

1. Найти wrapper, который вызывает `credits.aleo/unbond_public` и учитывает requested amount локально.
2. Сформировать состояние: bonded немного выше `10_000_000_000u64`.
3. Запросить малый partial unbond, оставляющий остаток меньше минимума.
4. Сравнить accounting wrapper-а с фактическим `credits.aleo/unbonding`.
5. Проверить, возникает ли reward/share drift или claimable mismatch.

Expected: wrapper учитывает фактический full unbond или запрещает такой partial request.  
Actual by source: core `credits.aleo` переводит в unbonding весь bonded amount.  
Impact: высокий только при доказанном wrapper mismatch; сам core behavior может быть намеренным.  
Reproducibility: высокая для core, средняя для exploit path.  
NonObviousness: высокая, потому что пользовательский input `requested` не равен фактическому effect.

### 3. Pondo: TVL oracle допускает 2% drift

**Статус:** `SOURCE_CONFIRMED_BEHAVIOR`  
**Контракты:** `pondo_protocol.aleo`, `validator_oracle.aleo`, `credits.aleo`, `delegator1-5.aleo`  
**Источник:** `aleo_context/raw/mainnet/program_sources/pondo_protocol.aleo.aleo:1223`

Суть: `finalize set_oracle_tvl` пересчитывает TVL из account/bonded/unbonding, но принимает reported TVL, если фактическое значение попадает в диапазон `reported * 98%` - `reported * 102%`.

PoC-ready шаги:

1. Взять текущее TVL состояние delegator accounts/bonded/unbonding.
2. Подать oracle TVL с максимальным допустимым смещением.
3. Найти функции, где TVL влияет на shares, rebalance, mint/redeem или reward accounting.
4. Выполнить действие до и после обновления TVL.
5. Сравнить asset/share ratio и reward allocation.

Expected: экономически значимое состояние должно использовать точный TVL или ограничивать drift так, чтобы нельзя было извлечь value.  
Actual by source: 2% окно допускается явно.  
Impact: средний/высокий при наличии downstream value extraction.  
Reproducibility: средняя, зависит от oracle permissions и downstream функций.  
NonObviousness: средняя/высокая, потому что проверка выглядит как защита, но может быть economic oracle surface.

### 4. `token_registry.aleo`: authorization expiry reordering

**Статус:** `SOURCE_CONFIRMED_EDGE_CASE`  
**Контракты:** `token_registry.aleo`, Arcane pools, Hyperlane warp tokens  

Суть: сценарий строится вокруг proof/transition, подготовленных до expiry, но finalize выполняется после `authorized_until`. Если registry проверяет `block.height` в finalize, ordering меняет outcome.

PoC-ready шаги:

1. Найти token authorization с коротким remaining window.
2. Подготовить chained operation до expiry.
3. Задержать finalize/callback на высоту после expiry.
4. Проверить, остается ли upstream state partially committed.
5. Проверить downstream pool/bridge accounting после failed registry finalize.

Expected: либо вся цепочка атомарно откатывается, либо downstream не фиксирует состояние до registry success.  
Actual by model: ordered finalize проходит, delayed finalize падает.  
Impact: пока низкий/средний, вероятнее griefing/DoS.  
Reproducibility: средняя.  
NonObviousness: высокая из-за block-height зависимого async ordering.

## 4. Опровергнутый сценарий: VLink duplicate attestor threshold

**Bug ID:** S1  
**Статус:** `REFUTED_BY_SOURCE`  
**Не подавать в bounty в текущем виде.**

Гипотеза: один и тот же non-zero attestor можно передать несколько раз и набрать threshold.

Фактический результат:

- `consume` проверяет pairwise uniqueness для non-zero attestors;
- zero-address placeholders допускаются, но не увеличивают signer count;
- после signature verification код сверяет число non-zero attestors с числом валидных signatures;
- модель с 5 одинаковыми attestors дает `transitionAccepts = false`.

Итог: как duplicate-attestor bug сценарий не воспроизводится. Это полезный результат: он очищает топ-10 от ложноположительного bridge-кейса.

## 5. Что считать bounty-ready прямо сейчас

Наиболее близкий к полноценному bounty report:

1. **USDCX previous freeze root window** - есть четкое source-confirmed поведение, direct bridge asset surface и понятный controlled PoC.
2. **`credits.aleo` partial->full unbond + wrapper accounting** - core behavior подтвержден; нужен один конкретный wrapper, где accounting ожидает requested amount.
3. **Pondo 2% TVL drift** - source-confirmed; станет сильным репортом, если доказать extraction через shares/rewards/rebalance.

Сценарии, которые пока лучше не подавать как баг:

- VLink duplicate attestor threshold: опровергнут кодом.
- DARA stale oracle: нет точной consumer-функции без max-age.
- Hyperlane/Arcane partial completion: потенциально сильные, но нужен exact path proof.

## 6. Минимальный следующий live/testnet план

1. Создать отдельный testnet wallet без mainnet средств.
2. Поднять RPC/CLI профиль только для testnet.
3. Для S5 воспроизвести freeze-root window на тестовом root update или в локальном fork-like harness.
4. Для S2 выбрать один staking wrapper и сравнить `requested_unbond` с фактическим `credits.aleo/unbonding`.
5. Для S4 найти функцию, где `pondo_protocol` TVL влияет на user-facing conversion, и проверить 2% drift на small-value inputs.

До этого безопасно формулировать результаты как verified-by-source and locally modeled, но не как on-chain exploited.
