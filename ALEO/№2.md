# Отчет N2: глубокий анализ логики и zk-proof механики Aleo

Дата анализа: 2026-05-12 UTC  
База данных этапа 1: `aleo_context/`  
Охват: 78 активных mainnet программ и 37 активных testnet программ из Provable metrics.

## 1. Executive summary

Этап 2 сфокусирован на скрытых логических и cryptographic edge cases: разрыв между zk-proof transition и finalize state update, lifecycle records/resources, deferred execution, callback chains, oracle/bridge state drift и non-intuitive сценарии.

Ключевой вывод: среди активных программ основной риск не в прямом использовании on-chain `snark.verify`, а в композиции:

- private proof constraints доказывают корректность локального transition;
- public state проверяется позже в `finalize`;
- `future`/`await` цепочки связывают несколько программ;
- часть критических условий зависит от текущего `block.height`, mappings и внешних программ.

Статический срез:

- `snark.verify`: 0 найденных в активной выборке.
- `sign.verify`: 37 использований.
- `commit.*`: 12 использований, в основном testnet privacy/payment flows.
- `await`: 551 использований.
- Основные риск-кластеры: `credits.aleo`, `token_registry.aleo`, staking wrappers, bridge contracts, Hyperlane-style mailbox/ISM/warp tokens, Pondo/validator oracle, DARA testnet DeFi.

Этот отчет не утверждает наличие эксплуатируемых уязвимостей без PoC. Он фиксирует наиболее вероятные места, где стандартные проверки могут вести себя неинтуитивно или где нужен targeted simulation.

## 2. Модель zk-proof и finalize в Aleo

В анализируемых программах proof constraints в основном задаются инструкциями transition:

- `assert.*`;
- арифметика и casts над private/public inputs;
- record consumption/output;
- hash/commit/signature checks;
- формирование `.future`.

Но public state mutations находятся в `finalize`. Поэтому валидный proof может:

- быть криптографически корректным для локальных private inputs;
- не пройти `finalize` из-за изменившегося mapping state;
- пройти `finalize`, но использовать state, отличный от state, который пользователь/интегратор ожидал при создании proof;
- стать non-executable после expiry/deferred window.

Главная audit-модель: проверять не только “доказывает ли proof локальный результат”, но и “совпадает ли state, который finalize реально читает, с state assumptions proof/caller”.

## 3. Приоритетные findings и edge-case кандидаты

### F-01. `token_registry.aleo`: authorization-validity drift между proof и finalize

Класс: zk-proof vs expected state / delayed authorization  
Статус: кандидат на targeted simulation  
Приоритет: высокий

Наблюдение:

- `transfer_public`, `transfer_public_as_signer`, `transfer_private`, `transfer_private_to_public`, `transfer_from_*` используют `authorized_until` и `block.height` в `finalize`.
- Для токенов с `external_authorization_required = true` proof может быть построен до истечения authorization window, но `finalize` проверяет `block.height <= authorized_until` уже в момент исполнения.
- Это корректно как защита, но неинтуитивно для интеграторов: private proof может быть валиден, а state transition неисполним.

Риск-сценарии:

- пользователь или router собирает proof near-expiry;
- mempool/ordering задерживает execution;
- downstream contract ожидает token movement, но callback/future не проходит;
- в multi-future цепочке часть локальных assumptions становится stale.

Что проверять на этапе PoC:

- все flows, где `token_registry.aleo/*future` передается в helper/router/pool;
- поведение при expiry на границе блока;
- разные ветки `balances` vs `authorized_balances` для external authorization.

### F-02. `credits.aleo`: non-intuitive unbond semantics и threshold-triggered full removal

Класс: Leo resource lifecycle / delayed execution / conditional path  
Статус: high-value invariant review  
Приоритет: высокий

Наблюдение:

- `unbond_public` ставит `unbonding.height = block.height + 360`.
- Для delegator branch вычисляется residual stake, затем при остатке ниже `10_000_000_000u64` или при определенных withdraw-authority условиях выбирается `ternary r18 r5.microcredits r2`.
- Это означает, что requested unbond amount может быть заменен на полный bonded amount.
- `claim_unbond_public` затем требует `block.height >= unbonding.height`, переводит средства на `withdraw` account и удаляет `unbonding`.

Риск-сценарии:

- caller ожидает partial unbond, но остаток ниже threshold приводит к full unbond;
- wrapper contracts должны синхронизировать локальные `bonded/totals` с фактической суммой, которую выбрал `credits.aleo`;
- при validator removal ветка может удалять `committee`/`bonded`, менять `delegated`, и downstream accounting обязан учитывать эту ветку.

Что проверять:

- все wrappers, которые вызывают `credits.aleo/unbond_public` и затем локально списывают `r2`;
- mismatch между requested amount и actual unbonded amount;
- orphaned local accounting, если core credits ветка выбрала full removal.

### F-03. Staking wrappers: callback chains вокруг `credits.aleo` создают accounting drift surface

Класс: deferred execution / callback chain / cross-contract state  
Статус: кандидат на инвариантные тесты  
Приоритет: высокий

Контракты:

- `whalepool_easystaking_v2.aleo`
- `whalepool_easystaking_v3.aleo`
- `betastaking.aleo`
- `zkwork_staking.aleo`
- `pondo_protocol.aleo`
- `delegator1-5.aleo`

Наблюдение:

- wrappers вызывают `credits.aleo/unbond_public`, `transfer_public`, `bond_public`, затем `await` соответствующие futures.
- Локальные mappings (`bonded`, `unbonding`, `totals`, `pool_info`, `unstakings`) обновляются после/вокруг `await`.
- В `whalepool_easystaking_v3.aleo` есть time-window checks через `mod block.height 28800u32`, лимиты unbonding и deferred claim.

Non-intuitive сценарии:

- valid wrapper proof может стать invalid из-за core `credits` state change;
- wrapper local `unbonding` может отражать сумму, которую wrapper считает списанной, а core `credits` может выбрать full-removal branch;
- admin/program_owner ветки обходят часть лимитов, поэтому нужно отдельно проверять privilege-gated accounting paths;
- `scope_check` меняет применимость time-window constraints.

Что проверять:

- invariant: `sum(local bonded + unbonding + available) == credits-held-by-wrapper`, с учетом rewards и full-removal branches;
- race/order тесты: два unbond/claim рядом с epoch/window boundary;
- owner/admin special paths.

### F-04. Bridge threshold verification: проверить uniqueness signer set и domain binding

Класс: cryptographic edge case / bridge replay  
Статус: требует PoC или ручного symbolic trace  
Приоритет: критический для bridge flows

Контракт: `vlink_token_bridge_v3.aleo`

Наблюдение:

- `consume` проверяет массив из 5 attestors через `contains attestors[r3[i]]`.
- Далее проверяет threshold через `bridge_settings[1u8]`.
- Replay защита основана на `in_packet_consumed[PacketId]`, где `PacketId` создается из `chain_id` и `sequence`.
- Signature checks выполняются до finalize; finalize повторно проверяет membership attestors и replay flag.

Потенциальные edge cases:

- если uniqueness адресов attestors не enforced до подсчета threshold, один attestor может быть засчитан более одного раза;
- если `PacketId = (chain, sequence)` не включает source service/sender/domain message hash, безопасность зависит от глобальности sequence на source chain;
- если supported service или chain меняется между proof и finalize, valid proof может fail или пройти с другим governance state.

Что проверять:

- duplicate attestor input vectors;
- одинаковая sequence от разных remote services;
- подпись одного сообщения с разными service/sender bindings;
- replay после governance updates threshold/attestors.

### F-05. `usdcx_bridge.aleo`: nullifier, Circle attestation и freeze-root window

Класс: bridge consistency / stale state / external proof binding  
Статус: требует targeted tests  
Приоритет: высокий

Наблюдение:

- Mint path проверяет Circle attester через `ecdsa.verify.digest.eth`.
- Replay защита: `contains nullifier[r2] == false`, затем `set true into nullifier[r2]`.
- Freeze-list root допускает текущий root либо предыдущий root в пределах `block_height_window`.
- `circle_attester[true]` имеет default hardcoded address через `get.or_use`.

Потенциальные edge cases:

- старый freeze root может оставаться валидным в window; нужно проверить, нельзя ли mint/burn проскочить сразу после freeze update;
- если attester mapping не инициализирован, используется default; governance assumptions должны явно учитывать default;
- nullifier должен быть строго связан с attestation hash/message. Если nullifier выводится из подмножества message fields, возможен replay/collision class.

Что проверять:

- freeze update boundary: root_updated_height + block_height_window;
- nullifier derivation against full Circle message;
- attester rotation around pending messages.

### F-06. Hyperlane-style `hyp_mailbox` / `hyp_ism_manager` / `hyp_warp_token_*`: callback chain и message-domain binding

Класс: bridge/zk proof interaction / callback chain  
Статус: high-value manual review  
Приоритет: высокий

Наблюдение:

- `hyp_mailbox.aleo` хранит `deliveries`, `dispatch_events`, `dispatch_id_events`, `process_events`, `registered_applications`.
- Warp tokens выполняют chains вида `dispatch -> burn` и `process -> mint`, через futures и `await`.
- В нескольких warp token контрактах фиксируются remote routers, hooks, ISM, mailbox, token registry/stablecoin mint/burn.

Риск-сценарии:

- message ID должен связывать version, nonce, origin, destination, sender, recipient, body;
- remote router registry должен быть неизменен для уже подтвержденных messages либо message proof должен явно bind-ить router;
- process/mint callback должен исключать partial completion: нельзя считать message delivered без mint или mint без process.

Что проверять:

- replay одного process future с разными recipient/token paths;
- router update между dispatch и process;
- required_hook/default_hook changes между proof и finalize.

### F-07. `pondo_protocol.aleo` и `validator_oracle.aleo`: stale reads и TVL tolerance

Класс: oracle stale reads / cross-contract state mismatch  
Статус: кандидат на экономическую симуляцию  
Приоритет: высокий

Наблюдение:

- `pondo_protocol.aleo/set_oracle_tvl` вызывает `validator_oracle.aleo/set_pondo_tvl`.
- После `await` пересчитывает TVL по `credits.aleo/account`, `credits.aleo/bonded`, `credits.aleo/unbonding` для `delegator1-5.aleo` и `pondo_protocol.aleo`.
- Допускается tolerance примерно `[98%, 102%]` от переданного TVL.
- Есть временное окно через `rem block.height 80888u32` и `lte r2 78008u32`.

Риск-сценарии:

- oracle TVL может быть принят с 2% drift;
- credits state может измениться между подготовкой proof и finalize;
- delegator balances/bonded/unbonding могут быть в переходном состоянии после unbond/rebalance;
- modulo-window boundary может создать non-intuitive fail/pass near epoch boundary.

Что проверять:

- TVL update во время массового unbond/rebalance;
- 2% tolerance exploitation при thin liquidity/large pending unbonding;
- stale `validator_oracle` allocation vs actual `credits` state.

### F-08. DARA testnet DeFi: oracle round monotonicity есть, freshness weak/implicit

Класс: oracle stale reads / DeFi edge case  
Статус: testnet, но полезно как pattern  
Приоритет: средний

Контракты:

- `dara_dp_credit_v5.aleo`
- `dara_dp_sol_v5.aleo`
- `dara_dp_eth_v5.aleo`
- `dara_dp_btc_v5.aleo`
- `dara_lend_v8.aleo`
- `dara_flash_v1.aleo`

Наблюдение:

- `update_oracle_price` требует operator membership и `round > previous_round`.
- Проверяет max price delta 15% относительно предыдущей цены.
- TWAP accumulates price/count и reset по `twap_window_blocks`.
- Многие order/batch paths используют `get.or_use ... false/0`.

Риск-сценарии:

- если oracle stops updating, consumers могут читать stale `oracle_price`, если freshness не проверяется в каждом action;
- first price path пропускает delta check, так как previous price = 0;
- batch approval и order consumed flags должны bind-ить exact order tuple, asset, side, expiry, price.

Что проверять:

- stale price usage после долгой паузы oracle;
- first-price initialization manipulation;
- batch ID collision / replay across assets.

### F-09. `get.or_use` defaults: missing-state masking

Класс: state initialization / non-intuitive defaults  
Статус: системный audit pattern  
Приоритет: средний

Наблюдение:

Многие программы используют defaults:

- `paused[true] false`;
- `minimum_burn_amount[true] 5000000u128`;
- `pool_paused[0u8] false`;
- `order_consumed[id] false`;
- `used_nonces[id] false`;
- balances/counters as `0`;
- roots/attesters/config with defaults.

Это часто удобно и может быть intentional. Но audit должен разделять:

- default как безопасный bootstrap;
- default как bypass при неинициализированном governance/config state;
- default как источник inconsistent accounting.

Особенно важно для bridge/stablecoin/DeFi, где отсутствие mapping value может трактоваться как “не paused”, “not consumed”, “not frozen”.

## 4. Leo resource lifecycle

### 4.1 Record consumption

На уровне Aleo record inputs должны быть consumed протоколом; прямой double-spend одного record невозможен при корректной VM semantics. Поэтому primary bug surface не “повторно использовать тот же record”, а:

- создать новый record с неожиданным owner;
- создать zero-value or dust record;
- потерять связь между private record и public accounting;
- использовать join/split так, что owner/token_id/authorization semantics меняются не так, как ожидает интегратор.

### 4.2 `puzzle_arcade_ticket_v002.aleo`

Наблюдения:

- `mint` создает `PuzzleArcadeTicket.record`, а `finalize mint` только проверяет, что `self.caller` в `registry`.
- `spend` возвращает остаточный ticket record, может быть zero amount.
- `join/join3/...` требуют входные amount > 0 и создают record owner = `self.signer`.

Non-intuitive scenarios:

- registered caller может mint-ить ticket на произвольный `owner`/`amount`, если registry governance позволяет;
- `spend` может оставлять zero-value record; downstream join rejects zero, но другие consumers должны учитывать dust/orphaned records;
- join переносит owner на `self.signer`, что нормально для consolidation, но важно для protocol assumptions.

### 4.3 Token records

`token_registry.aleo/Token.record` включает:

- `token_id`;
- `external_authorization_required`;
- `authorized_until`.

Edge cases:

- private token transfer сохраняет authorization metadata;
- переход private -> public зависит от finalize checks;
- routers должны не терять `authorized_until` и `external_authorization_required` при composition.

## 5. Deferred execution и partial completion

В Aleo futures + `await` обычно дают atomic composition на уровне accepted transaction. Тем не менее audit должен проверять:

- все futures awaited ли в wrapper finalize;
- не создаются ли public side effects до await, которые концептуально предполагают успех awaited future;
- не принимается ли external future без достаточной привязки к expected parameters;
- не может ли future быть получен из другого path с тем же типом, но не теми semantics.

High-risk examples:

- `arcn_puc_in_helper_v2_2_4.aleo`: несколько awaits на wrapped credits, token_registry и pool futures.
- `hyp_warp_token_*`: process/mint и dispatch/burn chains.
- `pondo_protocol.aleo`: awaits oracle/delegator futures и читает external credits mappings.
- staking wrappers: await core credits future затем меняют local accounting.

## 6. Межконтрактные расхождения состояния

### Bridge inconsistencies

Проверять:

- message replay state (`already_processed`, `deliveries`, `in_packet_consumed`, `nullifier`);
- domain separation message hash;
- source chain/service/router binding;
- signer/attestor uniqueness;
- threshold changes между proof и finalize;
- freeze/pause/root updates между proof и finalize.

### Oracle stale reads

Проверять:

- `validator_oracle.aleo`: allocation/top validators/ban state vs Pondo actions;
- DARA oracle price/round/TWAP;
- lending/flash contracts, где `price_update_block` есть, но freshness может проверяться не в каждом critical action.

### Token accounting drift

Проверять:

- `token_registry.aleo` balances vs authorized_balances;
- stablecoin balances vs freeze/pause state;
- wrapped credits vs `credits.aleo/account`;
- LP receipt/voucher flows in Arcane helpers.

## 7. Non-intuitive scenarios, где стандартные проверки могут не сработать

1. Proof валиден, но future не исполняется.
   - Причина: expiry, changed mapping, changed pause/freeze/root/threshold.

2. Requested unbond amount не равен фактически поставленному в unbonding.
   - Причина: threshold/full-removal branch in `credits.aleo`.

3. Bridge message подписан достаточным числом signatures, но signer set содержит duplicate или stale attestor state.
   - Нужно подтвердить uniqueness checks.

4. Старый freeze root еще допустим.
   - В bridge mint может быть grace window для предыдущего root.

5. `get.or_use false` трактует missing config как “разрешено”.
   - Без явной initialized guard это может быть bootstrap feature или bypass.

6. `block.height` modulo windows создают boundary failures.
   - Особенно staking/Pondo/Whalepool flows.

7. External future имеет правильный тип, но не тот economic context.
   - Нужно проверять, что finalize валидирует expected recipient/amount/token/pool, а не только awaits.

8. Private record owner меняется при join/consolidation.
   - Это нормально, но ломает протоколы, которые ожидали conservation of owner identity.

## 8. Shortlist для PoC / симуляции

Критический приоритет:

- `vlink_token_bridge_v3.aleo`: duplicate attestor, PacketId domain, threshold updates.
- `usdcx_bridge.aleo`: nullifier binding, freeze-root grace window, attester rotation.
- `hyp_mailbox.aleo` + `hyp_warp_token_*`: process/mint replay, router update, hook/ISM changes.
- `token_registry.aleo`: authorization expiry near block boundary, public/private transitions.

Высокий приоритет:

- `credits.aleo`: unbond full-removal branches, claim timing, withdraw authority.
- `whalepool_easystaking_v3.aleo`: core credits actual unbond vs local accounting.
- `pondo_protocol.aleo`: TVL tolerance and oracle stale reads.
- `validator_oracle.aleo`: allocation/top validator stale state.

Средний приоритет:

- `arcn_pool_v2_2_2.aleo` and helpers: multi-future pool/token/credits callback chains.
- `puzzle_arcade_ticket_v002.aleo`: registry-controlled mint and zero-value ticket remnants.
- DARA testnet suite: oracle freshness and batch/order replay patterns.

## 9. Рекомендованные тестовые сценарии

1. Boundary block tests:
   - `authorized_until == block.height`;
   - `block.height + 1`;
   - staking `block.height % 28800`;
   - Pondo `block.height % 80888`.

2. State drift tests:
   - build proof at state S;
   - mutate mapping before finalize;
   - execute future chain and verify fail/pass semantics.

3. Duplicate signer tests:
   - same attestor repeated in all positions;
   - mixed duplicate + valid;
   - threshold edge values.

4. Replay tests:
   - same sequence with different service;
   - same message with changed router;
   - same Circle message/nullifier in public/private mint variants.

5. Resource lifecycle tests:
   - zero-value record after spend;
   - join owner reset;
   - split/join across authorization-required tokens;
   - orphaned local mappings after failed callback chain.

6. Oracle stale tests:
   - no update for long window;
   - first price initialization;
   - round monotonic but economically stale;
   - TWAP count = 0 or reset boundary.
