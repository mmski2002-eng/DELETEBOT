# Отчет N3: сценарии глубоких багов и воспроизводимые PoC-модели Aleo

Дата: 2026-05-12 UTC  
База: отчеты `№1.md`, `№2.md`, исходники `aleo_context/raw/*/program_sources/`  
PoC-модель: `stage3_pocs/scenario_models.mjs`  
Результаты PoC: `stage3_pocs/scenario_results.json`

## 1. Назначение отчета

Цель этапа 3 - не доказать live exploit, а построить воспроизводимые multi-contract сценарии, где виден разрыв между expected behavior и actual behavior при:

- zk-proof transition vs delayed `finalize`;
- bridge threshold / replay / nullifier checks;
- staking unbond accounting;
- oracle stale reads;
- resource lifecycle;
- ordering и concurrent proof submissions.

Все PoC ниже являются локальными state-machine моделями. Они не отправляют транзакции в Aleo mainnet/testnet и не используют приватные ключи. Для перевода в полноценный exploit/test требуется отдельная Leo/snarkOS симуляция.

Запуск PoC:

```powershell
node .\stage3_pocs\scenario_models.mjs
```

Ожидаемый результат: `stage3_pocs/scenario_results.json`, где каждый сценарий имеет `status = edge_case_reproduced`.

## 2. Сценарий S1: VLink bridge duplicate attestor threshold

Класс: bridge / cryptographic threshold / signer uniqueness  
Приоритет: критический для проверки  
Статус: PoC-модель воспроизводит расхождение  

### Involved contracts

- `vlink_token_bridge_v3.aleo`

### Локальная опора в коде

- `mapping attestors`
- `mapping in_packet_consumed`
- `function consume`
- `finalize consume`
- `sign.verify` для массива `[address; 5]`
- `get.or_use in_packet_consumed[PacketId] false`

### Input data

```json
{
  "threshold": 3,
  "attestors": [
    "aleo_attestor_A",
    "aleo_attestor_A",
    "aleo_attestor_A",
    "aleo_attestor_A",
    "aleo_attestor_A"
  ],
  "signatureValidByPosition": [true, true, true, true, true]
}
```

### Steps

1. В bridge registry существует только один attestor: `aleo_attestor_A`.
2. В `consume` передается массив из 5 позиций, каждая позиция содержит тот же адрес `aleo_attestor_A`.
3. Для каждой позиции подается валидная подпись этого же attestor над тем же message digest.
4. Локальная модель считает accepted positions, как это делает позиционная threshold-логика без uniqueness.
5. Replay mapping `in_packet_consumed` еще не содержит `PacketId`.

### Expected outcome

Threshold должен считаться по уникальным attestors. Один уникальный signer не должен проходить threshold = 3.

```json
{
  "expected": false
}
```

### Actual modeled outcome

Позиционный подсчет принимает 5 подписей, хотя уникальный signer только 1.

```json
{
  "actual": true,
  "acceptedPositions": 5,
  "uniqueAccepted": 1
}
```

### Почему это важно

Если в реальном `consume` нет явной проверки `r3[0] != r3[1] != ...`, один attestor может быть засчитан несколько раз. Это превращает threshold bridge в single-signer bridge.

### Что подтвердить полноценным PoC

- Собрать реальный input vector с одинаковым attestor address в 5 позициях.
- Проверить, принимает ли `sign.verify` одинаковую подпись в каждой позиции.
- Проверить, есть ли скрытая uniqueness проверка в пропущенных участках transition.
- Проверить оба digest branches, так как код считает подписи по двум message digests.

## 3. Сценарий S2: `credits.aleo` partial unbond превращается в full unbond

Класс: staking / resource lifecycle / accounting drift  
Приоритет: высокий  
Статус: PoC-модель воспроизводит расхождение

### Involved contracts

- `credits.aleo`
- `whalepool_easystaking_v3.aleo`
- потенциально любые wrappers, вызывающие `credits.aleo/unbond_public`

### Локальная опора в коде

В `credits.aleo/finalize unbond_public`:

- `add block.height 360u32`
- `sub r5.microcredits r2`
- `lt residual 10_000_000_000u64`
- `ternary r18 r5.microcredits r2`
- `remove bonded[r1]`

### Input data

```json
{
  "bonded": "10000000500",
  "requested": "1000",
  "minDelegatorStake": "10000000000"
}
```

### Steps

1. Delegator имеет bonded amount `10_000_000_500`.
2. Пользователь запрашивает partial unbond `1_000`.
3. Остаток после partial unbond: `9_999_999_500`.
4. Остаток ниже минимального порога `10_000_000_000`.
5. Ветка `ternary` выбирает не requested amount, а весь `bonded`.

### Expected outcome

Пользователь ожидает, что в unbonding попадет только `1_000`.

```json
{
  "expected": "1000"
}
```

### Actual modeled outcome

В unbonding попадает весь bonded amount.

```json
{
  "actual": "10000000500",
  "extraUnbonded": "9999999500"
}
```

### Почему это важно

Это может быть intentional protocol rule, но для wrappers это опасный accounting edge case. Если wrapper локально списывает requested amount, а core `credits.aleo` фактически unbond-ит full amount, появляется drift между:

- local `bonded`;
- local `unbonding`;
- `credits.aleo/bonded`;
- `credits.aleo/unbonding`;
- accounting totals.

### Что подтвердить полноценным PoC

- Проверить wrapper paths, где после `await credits.aleo/unbond_public.future` локальная сумма берется из requested input, а не из actual core branch.
- Проверить owner/admin special paths в `whalepool_easystaking_v3.aleo`.
- Проверить claim после 360 блоков и итоговую сумму в `account[withdraw]`.

## 4. Сценарий S3: `token_registry.aleo` authorization expiry через reordering

Класс: zk-proof trigger + delayed finalize + cross-contract timing  
Приоритет: высокий  
Статус: PoC-модель воспроизводит расхождение

### Involved contracts

- `token_registry.aleo`
- `arcn_pool_v2_2_2.aleo`
- `hyp_warp_token_*.aleo`
- любые routers/helpers, принимающие `token_registry.aleo/*future`

### Локальная опора в коде

В `token_registry.aleo`:

- `authorized_until`
- `external_authorization_required`
- `lte block.height authorized_until`
- `balances` / `authorized_balances`
- `.future` и `await` в downstream contracts

### Input data

```json
{
  "proofHeight": 999,
  "authorizedUntil": 1000,
  "finalizeHeightIfOrdered": 1000,
  "finalizeHeightIfDelayed": 1001
}
```

### Steps

1. Пользователь строит proof на высоте 999.
2. Authorization действует до блока 1000.
3. Если transaction попадает в блок 1000, finalize проходит.
4. Если из-за reordering/congestion transaction попадает в блок 1001, proof все еще криптографически валиден, но finalize падает.
5. Downstream contract, который ожидал token movement, получает failed future chain.

### Expected outcome

Интегратор ожидает, что proof, собранный до expiry, исполним.

```json
{
  "expected": true
}
```

### Actual modeled outcome

Finalize проверяет текущий `block.height`, и delayed execution падает.

```json
{
  "actual": false,
  "proofLocallyValid": true,
  "delayedPasses": false
}
```

### Почему это важно

Это может приводить к:

- griefing через ordering delay;
- stuck user workflows;
- failed multi-contract atomic chain;
- non-intuitive UX/security assumption в bridge/router/pool.

### Что подтвердить полноценным PoC

- Построить transfer proof near-expiry.
- Исполнить в блоке `authorized_until` и `authorized_until + 1`.
- Повторить через helper, который awaits token future.

## 5. Сценарий S4: Pondo TVL tolerance принимает stale/oracle drift

Класс: oracle stale reads + staking accounting  
Приоритет: высокий  
Статус: PoC-модель воспроизводит acceptance drift

### Involved contracts

- `pondo_protocol.aleo`
- `validator_oracle.aleo`
- `credits.aleo`
- `delegator1.aleo` - `delegator5.aleo`

### Локальная опора в коде

В `pondo_protocol.aleo/finalize set_oracle_tvl`:

- `await validator_oracle.aleo/set_pondo_tvl.future`
- reads from `credits.aleo/account`
- reads from `credits.aleo/bonded`
- reads from `credits.aleo/unbonding`
- range check: `reported * 98 / 100 <= recomputed <= reported * 102 / 100`
- window: `block.height % 80888 <= 78008`

### Input data

```json
{
  "reportedTvl": "1020000000000",
  "actualRecomputedTvl": "1000000000000",
  "tolerance": "98%-102% of reported value"
}
```

### Steps

1. Oracle reports TVL = `1_020_000_000_000`.
2. Pondo recomputes actual TVL from credits/delegator states = `1_000_000_000_000`.
3. Contract computes lower bound `999_600_000_000`.
4. Contract computes upper bound `1_040_400_000_000`.
5. Actual recomputed TVL falls inside range.

### Expected outcome

Для accounting-critical path strict equality or much tighter invariant might be expected.

```json
{
  "expected": false
}
```

### Actual modeled outcome

2% drift accepted.

```json
{
  "actual": true,
  "acceptedDrift": "20000000000"
}
```

### Почему это важно

Tolerance может быть intentional anti-noise rule. Но рядом с rebalance, pending unbonding, validator allocation update или reward settlement 2% drift может стать экономическим edge case.

### Что подтвердить полноценным PoC

- Симулировать mass unbond/rebalance перед `set_oracle_tvl`.
- Проверить, можно ли выбрать reported TVL, который проходит range, но влияет на shares/rewards/commission.
- Проверить modulo boundary `block.height % 80888`.

## 6. Сценарий S5: USDCX bridge previous freeze root grace window

Класс: bridge + freeze-list stale root + nullifier  
Приоритет: высокий  
Статус: PoC-модель воспроизводит расхождение

### Involved contracts

- `usdcx_bridge.aleo`
- `usdcx_freezelist.aleo`
- `usdcx_stablecoin.aleo`

### Локальная опора в коде

В `usdcx_bridge.aleo/finalize mint_private`:

- `paused[true]`
- current freeze root `freeze_list_root[1u8]`
- previous freeze root `freeze_list_root[2u8]`
- `root_updated_height + block_height_window > block.height`
- `ecdsa.verify.digest.eth`
- `nullifier`
- `await usdcx_stablecoin.aleo/mint_*`

### Input data

```json
{
  "rootUpdatedHeight": 50000,
  "blockHeightWindow": 360,
  "mintHeight": 50100,
  "usingPreviousRoot": true,
  "nullifierPreviouslyUsed": false
}
```

### Steps

1. Freeze root обновлен на высоте 50 000.
2. Пользователь использует предыдущий root.
3. Mint происходит на высоте 50 100.
4. Grace window действует до 50 360.
5. Nullifier еще не использован.
6. Attestation signature валидна.

### Expected outcome

Если адрес уже заморожен в новом root, mint должен быть заблокирован немедленно.

```json
{
  "expected": false
}
```

### Actual modeled outcome

Предыдущий root все еще принимается в grace window.

```json
{
  "actual": true,
  "previousRootValidUntil": 50360
}
```

### Почему это важно

Если grace window является intentional compatibility feature, это нужно явно учитывать как security trade-off. Если нет, возникает window, где новый freeze state еще не обязателен.

### Что подтвердить полноценным PoC

- Mint с old root сразу после freeze update.
- Mint после `root_updated_height + block_height_window`.
- Rotation `circle_attester[true]` вокруг pending attestation.
- Nullifier binding к полному Circle message.

## 7. Сценарий S6: DARA stale oracle order acceptance

Класс: oracle stale reads + DeFi order execution  
Приоритет: средний, testnet pattern  
Статус: PoC-модель воспроизводит расхождение

### Involved contracts

- `dara_dp_credit_v5.aleo`
- `dara_lend_v8.aleo`
- `dara_flash_v1.aleo`

### Локальная опора в коде

В DARA testnet suite:

- `oracle_price`
- `oracle_round`
- `price_update_block`
- `twap_cum_price`
- `twap_last_reset`
- `batch_approved`
- `order_consumed`
- bounded delta check around 15%

### Input data

```json
{
  "currentHeight": 100000,
  "priceUpdateBlock": 90000,
  "assumedMaxAge": 3600,
  "oracleRoundIncreased": true,
  "deltaWithinLimit": true
}
```

### Steps

1. Oracle update был на высоте 90 000.
2. Текущая высота 100 000.
3. Цена устарела на 10 000 блоков.
4. Round monotonicity и delta limit выглядят валидно.
5. Consumer path не проверяет freshness в модели.

### Expected outcome

DeFi order/loan/flash flow должен reject stale oracle data.

```json
{
  "expected": false
}
```

### Actual modeled outcome

При отсутствии freshness check order принимается.

```json
{
  "actual": true,
  "age": 10000,
  "consumerChecksFreshness": false
}
```

### Почему это важно

Даже testnet-контракт полезен как паттерн: monotonic round и bounded delta не заменяют max-age check. Stale price может быть безопасным криптографически, но неверным экономически.

### Что подтвердить полноценным PoC

- Найти все consumer paths, где читается `oracle_price`.
- Проверить наличие `block.height - price_update_block <= max_age`.
- Смоделировать fill/borrow/flash при stale price.

## 8. Multi-contract exploit-chain templates

### Template A: bridge -> token mint -> DeFi deposit

Контракты:

- `vlink_token_bridge_v3.aleo` или `usdcx_bridge.aleo`
- `token_registry.aleo` / `usdcx_stablecoin.aleo`
- `arcn_pool_v2_2_2.aleo`

Steps:

1. Bridge message/mint проходит при edge condition: duplicate attestor или stale freeze root.
2. Minted public/private token появляется в token/stablecoin contract.
3. Token сразу используется в pool deposit/swap before governance detects issue.
4. Если bridge replay/nullifier позже блокируется, pool уже принял accounting state.

Expected:

- Bridge должен reject invalid/stale proof before any token accounting.

Actual risk:

- Если bridge condition проходит, downstream DeFi считает minted token валидным.

### Template B: token authorization expiry -> router DoS

Контракты:

- `token_registry.aleo`
- `arcn_puc_*`
- `arcn_pool_v2_2_2.aleo`

Steps:

1. Пользователь создает proof near `authorized_until`.
2. Router собирает multi-future transaction.
3. Transaction попадает в следующий блок.
4. `token_registry` future fails.
5. Entire router action fails.

Expected:

- Router должен заранее учитывать expiry margin.

Actual risk:

- Ordering griefing / repeated failed transactions / stuck UX.

### Template C: credits unbond -> wrapper accounting drift -> claim

Контракты:

- `credits.aleo`
- staking wrapper

Steps:

1. User/wrapper requests partial unbond that leaves residual below minimum.
2. Core `credits.aleo` moves full bonded amount into unbonding.
3. Wrapper local accounting updates by requested amount or special branch.
4. After 360 blocks, claim changes public account.

Expected:

- Wrapper accounting exactly matches actual `credits.aleo` branch.

Actual risk:

- Orphaned local bonded/unbonding/totals if branch mismatch exists.

### Template D: oracle stale TVL -> rebalance/reward drift

Контракты:

- `validator_oracle.aleo`
- `pondo_protocol.aleo`
- `credits.aleo`
- delegators

Steps:

1. Oracle reports stale but tolerance-compatible TVL.
2. Pondo recomputes actual TVL and accepts within 98%-102%.
3. Rebalance/reward/share logic consumes accepted TVL.
4. Later state converges, leaving accounting skew.

Expected:

- TVL should be fresh and tightly bound to current credits state.

Actual risk:

- Tolerance accepts economically meaningful drift.
