## 1. Методика оценки

Каждый сценарий оценивался по 4 критериям от 1 до 5:

- Impact: влияние на user assets, TVL, escrow, bridge mint/burn, staking accounting.
- Reproducibility: насколько реалистично повторить сценарий в локальном test harness или fork-like simulation.
- NonObviousness: насколько баг скрыт за zk/finalize/callback/bridge логикой.
- AleoSpecificComplexity: насколько сценарий зависит именно от Aleo/Leo/futures/finalize/private records/bridge composition.

Итоговый балл: сумма 4 критериев, максимум 20.

Статусы:

- PoC-model ready: уже есть локальная модель в `stage3_pocs/scenario_models.mjs`.
- PoC-ready: нет полной модели, но есть конкретные контракты, inputs и проверяемый invariant.
- Needs narrowing: перспективно, но нужно сузить конкретный execution path.

## 3. Rank 1: VLink duplicate attestor threshold

Контракт: `vlink_token_bridge_v3.aleo`  
Impact: критический, потенциальный bridge threshold bypass.  
Почему bounty-worthy: если подтверждается, один attestor может имитировать threshold и провести inbound packet.

### POC-ready инструкция

1. Взять `vlink_token_bridge_v3.aleo/consume`.
2. Подготовить state:
   - `attestors[A] = true`;
   - `bridge_settings[1u8] = 3`;
   - `bridge_settings[3u8] = 1`;
   - `supported_chains[chain_id] = true`;
   - `supported_services[caller] = true`;
   - `in_packet_consumed[PacketId(chain_id, sequence)] = false`.
3. Сформировать input:
   - `r3 = [A, A, A, A, A]`;
   - подпись `A` повторить во всех позициях;
   - использовать одинаковый valid digest branch.
4. Expected: reject, потому что unique attestors = 1 < threshold.
5. Actual to prove: accepted, если позиционный счетчик достигает threshold.

### Minimal model

```powershell
node .\stage3_pocs\scenario_models.mjs
```

Смотреть `S1_vlink_duplicate_attestor_threshold`.

## 4. Rank 2: USDCX bridge previous freeze root window

Контракты:

- `usdcx_bridge.aleo`
- `usdcx_freezelist.aleo`
- `usdcx_stablecoin.aleo`

Impact: высокий/критический, потому что bridge mint может затронуть wrapped/stablecoin assets.  
Почему bounty-worthy: freeze list обычно ожидается как немедленная защита; grace window может позволить mint по старому root.

### POC-ready инструкция

1. Установить freeze-list state:
   - current root содержит frozen recipient;
   - previous root не содержит frozen recipient;
   - `root_updated_height = H`;
   - `block_height_window = W`.
2. Выбрать `block.height = H + 100`, где `100 < W`.
3. Подготовить Circle attestation с unused nullifier.
4. Вызвать `usdcx_bridge.aleo/mint_public` или `mint_private` с previous root.
5. Expected: reject, потому что recipient frozen in current root.
6. Actual to prove: accepted до `H + W`, если previous root branch проходит.

### Minimal model

Смотреть `S5_usdcx_bridge_previous_freeze_root_window`.

## 5. Rank 3: Hyperlane mailbox/warp process-mint replay or router drift

Контракты:

- `hyp_mailbox.aleo`
- `hyp_ism_manager.aleo`
- `hyp_dispatch_proxy.aleo`
- `hyp_warp_token_usdc/usdt/wbtc/eth/sol/usad.aleo`
- `token_registry.aleo` или stablecoin program

Impact: критический, если удается mint without valid current route/process binding.  
Почему bounty-worthy: сложная bridge callback composition, высокая non-obviousness.

### POC-ready инструкция

1. Выбрать один warp token, например `hyp_warp_token_usdc.aleo`.
2. Зафиксировать message:
   - origin domain;
   - destination domain;
   - sender;
   - recipient;
   - token amount;
   - body.
3. Выполнить `hyp_mailbox/process` future для message.
4. Между process proof и finalize изменить один из:
   - remote router;
   - default ISM;
   - required hook;
   - registered application metadata.
5. Передать process future в warp token mint callback.
6. Expected: mint должен быть bound к route/ISM/router на момент доказанного message.
7. Actual to prove: mint проходит с новым route state или process event может быть reused in unintended context.

### Evidence to collect

- mapping diff before/after router update;
- message ID до и после update;
- whether `deliveries` prevents second process;
- whether mint callback checks recipient/token/router directly.

## 6. Rank 4: Credits partial unbond -> full unbond wrapper drift

Контракты:

- `credits.aleo`
- `whalepool_easystaking_v3.aleo`
- также проверить `whalepool_easystaking_v2.aleo`, `betastaking.aleo`, `zkwork_staking.aleo`

Impact: высокий, влияет на staking accounting и claimable funds.  
Почему bounty-worthy: core behavior может быть intentional, но wrapper drift вокруг него часто bounty-relevant.

### POC-ready инструкция

1. State:
   - `credits.aleo/bonded[user].microcredits = 10_000_000_500`;
   - `credits.aleo/delegated[validator]` достаточно для branch;
   - `withdraw[user]` настроен.
2. Вызвать wrapper или direct `credits.aleo/unbond_public(user, 1_000)`.
3. Проверить, что residual `< 10_000_000_000`.
4. Expected wrapper accounting: unbonding += `1_000`.
5. Actual core accounting: unbonding += `10_000_000_500`.
6. Через 360 блоков вызвать claim и сравнить local totals vs `credits.aleo/account`.

### Minimal model

Смотреть `S2_credits_partial_request_full_unbond`.

## 7. Rank 5: Pondo TVL tolerance stale oracle drift

Контракты:

- `pondo_protocol.aleo`
- `validator_oracle.aleo`
- `credits.aleo`
- `delegator1-5.aleo`

Impact: высокий, если TVL влияет на shares, rewards, commission или rebalance.  
Почему bounty-worthy: oracle drift + cross-contract reads + tolerance window сложно заметить.

### POC-ready инструкция

1. Собрать state vector:
   - `credits.aleo/account[delegator1-5]`;
   - `credits.aleo/bonded[delegator1-5]`;
   - `credits.aleo/unbonding[delegator1-5]`;
   - `credits.aleo/account[pondo_protocol.aleo]`.
2. Выбрать `actual_tvl = 1_000_000_000_000`.
3. Передать `reported_tvl = 1_020_000_000_000`.
4. Убедиться, что `block.height % 80888 <= 78008`.
5. Вызвать `set_oracle_tvl`.
6. Expected: reject stale/biased TVL.
7. Actual to prove: accepted внутри 98%-102% диапазона.
8. Затем показать downstream effect: shares/reward/rebalance accounting changes.

### Minimal model

Смотреть `S4_pondo_tvl_tolerance_stale_oracle`.

## 8. Rank 6: Token registry authorization expiry reordering

Контракты:

- `token_registry.aleo`
- `arcn_pool_v2_2_2.aleo`
- `arcn_puc_*`
- `hyp_warp_token_*`

Impact: средний/высокий. Скорее DoS/griefing/stuck workflow, чем direct asset theft.  
Почему bounty-worthy: Aleo-specific split proof/finalize плюс external authorization expiry.

### POC-ready инструкция

1. Создать token с `external_authorization_required = true`.
2. Создать balance/record с `authorized_until = H`.
3. Построить transfer proof на `H - 1`.
4. Выполнить transaction на `H`: expected pass.
5. Выполнить equivalent transaction на `H + 1`: actual fail.
6. Повторить через helper/router, который awaits `token_registry.aleo/*future`.
7. Доказать, что upstream proof валиден, но downstream atomic chain fails из-за finalize height.

### Minimal model

Смотреть `S3_token_registry_authorization_expiry_reordering`.

## 9. Rank 7: Arcane multi-future pool/token/credits callback mismatch

Контракты:

- `arcn_pool_v2_2_2.aleo`
- `arcn_puc_in_helper_v2_2_4.aleo`
- `arcn_puc_out_helper_swap_v2_2_6.aleo`
- `wrapped_credits.aleo`
- `token_registry.aleo`
- `credits.aleo`

Impact: высокий, если LP/share/pool accounting расходится с token transfer futures.  
Почему bounty-worthy: multi-future callback chains с 3-5 awaits являются типичной зоной hidden bugs.

### POC-ready инструкция

1. Выбрать helper path:
   - create pool;
   - add liquidity;
   - swap;
   - remove liquidity.
2. Подготовить token A with authorization expiry near current block.
3. Подготовить credits/wrapped credits future.
4. Сконструировать transaction, где:
   - one token future succeeds;
   - second token future fails due to expiry/freeze/authorization;
   - pool future already computed expected voucher/LP result.
5. Expected: entire chain reverts without state drift.
6. Actual to prove: any pool/voucher/local mapping state changes despite failed token side or accepts mismatched amount/token.

### Evidence to collect

- all futures awaited;
- exact order of awaits;
- pool mappings before/after;
- token balances before/after.

## 10. Rank 8: USDCX nullifier binding / public-private mint replay class

Контракты:

- `usdcx_bridge.aleo`
- `usdcx_stablecoin.aleo`

Impact: критический if nullifier not bound to full message.  
Почему bounty-worthy: bridge mint replay/collision is direct asset impact.

### POC-ready инструкция

1. Взять one valid Circle message.
2. Извлечь fields:
   - digest;
   - nullifier;
   - recipient;
   - amount;
   - source/destination domain.
3. Попробовать использовать same attestation/nullifier in:
   - `mint_public`;
   - `mint_private`;
   - altered recipient path;
   - altered metadata path.
4. Expected: every altered variant reject, and same nullifier cannot mint twice.
5. Actual to prove: any variant passes before `nullifier` is set or derives nullifier from insufficient fields.

### Notes

Это требует точной реконструкции message serialization. Если код уже binds `keccak(message)` and nullifier robustly, сценарий закрывается.

## 11. Rank 9: DARA stale oracle consumer acceptance

Контракты:

- `dara_dp_credit_v5.aleo`
- `dara_dp_sol_v5.aleo`
- `dara_dp_eth_v5.aleo`
- `dara_dp_btc_v5.aleo`
- `dara_lend_v8.aleo`
- `dara_flash_v1.aleo`

Impact: средний, потому что testnet, но high-signal для будущего mainnet DeFi.  
Почему bounty-worthy: stale oracle is classic economic bug; Aleo-specific часть в private orders + finalize mappings.

### POC-ready инструкция

1. Установить oracle price на высоте `H`.
2. Не обновлять oracle до `H + 10_000`.
3. Выполнить order/loan/flash path, который читает `oracle_price`.
4. Проверить, есть ли `block.height - price_update_block <= max_age`.
5. Expected: reject stale price.
6. Actual to prove: accepted if only round/delta checked.

### Minimal model

Смотреть `S6_dara_stale_oracle_order_acceptance`.

## 12. Rank 10: Puzzle ticket arbitrary mint / zero-ticket remnants

Контракт:

- `puzzle_arcade_ticket_v002.aleo`

Impact: низкий/средний, зависит от downstream value of tickets.  
Почему bounty-worthy: high activity NFT/game asset, simple reproducibility, hidden resource lifecycle edge.

### POC-ready инструкция

1. Получить или смоделировать registered caller in `registry`.
2. Вызвать `mint(owner, amount)` with arbitrary `owner` and high `amount`.
3. Проверить, ограничивает ли registry caller amount/owner вне этого контракта.
4. Вызвать `spend(ticket, full_amount)`.
5. Получить zero-value ticket record.
6. Передать zero-ticket в downstream consumers, кроме `join`, и проверить, принимают ли они его.
7. Expected: arbitrary mint/zero remnants не должны влиять на game/economic logic.
8. Actual to prove: downstream принимает zero/dust ticket или registry minter может создавать value без supply cap.

## 13. Что не вошло в top-10

- Generic `get.or_use false` bootstrap issues: слишком широкий класс, нужен конкретный exploit path.
- Pure authorization expiry без downstream effect: reproduces failure, но impact ниже.
- Static hash/commit usage in privacy payment testnet contracts: нужен отдельный cryptographic review.
- ANS price stale path: перспективно, но пока ниже bridge/staking/DeFi по impact.

## 14. Рекомендуемый порядок работы для bounty

1. Сначала S1: минимальный набор входов, максимальный impact, очень сильный bounty profile.
2. Затем S5/S8: USDCX bridge mint/freeze/nullifier, direct asset impact.
3. Затем S4: Pondo TVL, если удается показать downstream reward/share effect.

5. Затем S7: Arcane helper callback mismatch, сложнее, но потенциально high impact.
6. S3/S9/S10 использовать как backup или supporting findings.
