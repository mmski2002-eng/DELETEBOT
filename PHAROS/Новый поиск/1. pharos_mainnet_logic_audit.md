## 2. Mental Model

Pharos Mainnet is an EVM-compatible L1 where normal Ethereum-style accounts, transactions, contracts, logs, balances, and gas exist under chain id `1672`. The distinctive design claims are not the existence of EVM state itself, but the way execution and surrounding systems are organized:

1. Consensus aims for responsive BFT-style ordering without fixed block timing and with simultaneous proposals.
2. Execution is parallelized using scheduling, read-write hints, dependency analysis, optimistic execution, conflict resolution, and asynchronous state writes.
3. Finality is split into ordering finality, transaction finality, and block finality. This creates an important semantic surface: a component may treat execution result, block header availability, and block-wide finality as different stages.
4. The VM surface may include both EVM and WASM under a single runtime, with possible cross-VM calls.
5. SPNs are specialized environments connected to the Primary Network through manager/registry/mailbox/bridge flows, relayers, proofs, headers, and restaking incentives.
6. Cross-chain value/data may use Chainlink CCIP and/or LayerZero for application-level integrations. These external systems have their own finality, message identity, fee, retry, and execution semantics.
7. Indexers, explorers, relayers, full nodes, and RPC providers observe or forward state, but the chain state must remain the canonical source.

The most important audit idea: do not ask "which known bug exists?" Ask where two honest components can see the same action as different in timing, meaning, scope, authority, or accounting.

## 5. Event Ordering

Strict or near-strict order candidates:

1. A transaction must be signed for chain id `1672` before it should be accepted as a Pharos Mainnet action.
2. Sender nonce/account balance must be valid before inclusion.
3. Execution result must be determined before receipt/logs are canonical.
4. For cross-SPN: source action -> relayer submission with proof/header -> Primary verification/recording -> target SPN retrieval/execution.
5. For bridge/OFT/CCIP app flows: source-side debit/lock/burn must correspond to at most one destination-side credit/mint/unlock.
6. For restaking: stake -> certificate -> SPN allocation -> reward/slash/redeem; slashing must affect the correct certificate and owner scope.

Can happen in variable order:

- RPC observations across providers.
- Indexer display vs direct RPC state.
- Relayer retries and message execution attempts.
- Oracle/data updates vs user settlement.
- Block header access vs full block finality, per Pharos pipeline finality design.

Can repeat:

- Transaction broadcast.
- Message forwarding.
- Quote refresh.
- Recovery/rescue attempts if public.
- Indexer reprocessing.
- Cross-chain execution retry.

Can partially happen:

- Source-side message recorded but target execution pending.
- Event emitted but downstream worker not processed.
- Header available but block finality delayed.
- Transaction finality observed but indexer/API lagging.
- Gas charged by limit while refund semantics differ from EVM developer expectation. Post-triage note: this was not observed in five sampled mainnet txs; sampled balance deltas matched `gasUsed * effectiveGasPrice`.

## 11. Attack Stories (High-Level, Non-Destructive)

### Story A: Transaction-Final But Not Block-Final

Broken Assumption: all components use "final" identically.

Weird State: a relayer or indexer treats a transaction result as actionable while another component waits for block finality or confirmations.

Why Normal Reasoning Misses It: Pharos explicitly splits ordering, transaction, and block finality; UI often compresses all three into one status.

Minimum Required Powers: ordinary user transaction plus ability to observe RPC/indexer/API status, or a relayer in a test setup.

Execution Shape: submit a benign app transaction on a fork/local simulation, observe receipt availability, block depth, explorer/API status, and downstream message/settlement status at each stage.

Components That Disagree: RPC receipt, block finality monitor, indexer, relayer, UI.

Expected Divergence: finality, settlement status, UI status.

Potential Impact: premature message execution, stale oracle/action trigger, incorrect user-visible completion.

Evidence Needed: transaction trace, block depth, indexer record, relayer queue record, app storage flags.

Confidence: Medium. Reachability: Medium. Impact: Medium to High depending app.

Next Test: build an event-vs-state-vs-block-depth comparison for a mainnet app transaction using read-only calls.

Expected If True: API/UI shows completion before the contract/finality policy can justify it.

Expected If False: every downstream component waits for an explicit finality threshold.

Status: NEEDS EVIDENCE.

### Story B: Message Identity Collapses Across SPN Domains

Broken Assumption: a message id is globally unique without explicit domain binding.

Weird State: source SPN, Primary mailbox, and target SPN interpret the same bytes under different scopes.

Why Normal Reasoning Misses It: docs show a clean four-step flow but do not provide hash inputs or consumed-marker scope.

Minimum Required Powers: ability to create a benign message in a local/fork SPN simulation or inspect deployed mailbox/bridge code.

Execution Shape: compare message hash construction, proof verification input, mailbox storage key, and target consumed flag.

Components That Disagree: SPN source, Primary mailbox, target SPN adapter, indexer.

Expected Divergence: message lifecycle, replay/consumption state, accounting entry.

Potential Impact: duplicate execution or blocked legitimate execution.

Evidence Needed: SPN manager/mailbox/bridge contract code, storage diff, event logs, proof payload.

Confidence: Low to Medium. Reachability: UNKNOWN. Impact: High if live bridge assets depend on it.

Next Test: obtain mainnet SPN manager/mailbox/bridge addresses and inspect message id domain separation.

Expected If True: message id omits one of chain id, SPN id, source contract, target contract, nonce, or route id.

Expected If False: consumed mapping is scoped by full source/target/domain tuple.

Status: NEEDS EVIDENCE.

### Story C: Refund and Delayed Settlement Both Become Plausible

Broken Assumption: timeout/refund means settlement can no longer happen.

Weird State: source-side refund eligibility exists while a delayed relayer/target execution path remains valid.

Why Normal Reasoning Misses It: happy path treats timeout as liveness protection and settlement as success, not as two independently observable states.

Minimum Required Powers: ordinary user, ability to wait until timeout, ability to trigger public retry/recovery in test/fork.

Execution Shape: create benign pending message/order, let timeout boundary pass, call refund/cancel path, then attempt delayed execution/retry in local/fork environment.

Components That Disagree: source contract, target contract, relayer, UI/indexer.

Expected Divergence: refund eligibility, settlement status, balance/credit.

Potential Impact: user or solver gets both refund and benefit, or value becomes stuck.

Evidence Needed: lifecycle flags, consumed flags, balance deltas, emitted events, relayer retry policy.

Confidence: Medium as a class, Low for Pharos until code is available. Reachability: UNKNOWN. Impact: High for bridges/orders.

Next Test: inspect timeout checks and target execution checks in deployed app/bridge contracts.

Expected If True: refund does not mark the target message impossible or target execution does not read refund/cancel state.

Expected If False: single lifecycle state machine blocks settlement after refund.

Status: NEEDS EVIDENCE.

### Story D: Gas Refund Economics Differ From Developer Expectation

Broken Assumption: EVM-style refund tracking means the user's economic charge is reduced like expected.

Weird State: a transaction is logically successful or failed in a way the app expects to be cheap, but Pharos charges by gas limit at inclusion time and refund tracking does not affect charge per docs.

Why Normal Reasoning Misses It: apps ported from Ethereum may reason about gas refunds as economic behavior, while Pharos docs separate refund tracking from charge.

Minimum Required Powers: ordinary transaction in fork/local simulation; no mainnet destructive action.

Execution Shape: simulate calls that clear storage or rely on refund-heavy paths with exact and buffered gas limits; compare gas used, gas limit charged, user balance delta, event/state result.
